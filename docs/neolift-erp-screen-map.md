# НеоЛифт ERP/PWA — полный UX/UI screen map внутренней системы

## 0. Назначение документа

Документ описывает production-ready UX/UI screen map внутренней ERP/PWA системы «НеоЛифт» для механиков, диспетчеров и руководителей. Это рабочая field-service система для оформления, проверки и закрытия заказ-нарядов по обслуживанию и ремонту лифтов.

Документ не описывает маркетинговый сайт, лендинг, промо-страницы, hero sections, pricing blocks, testimonials, feature cards или onboarding-презентации. Все экраны являются операционными интерфейсами внутренней системы.

Главная UX-задача: механик должен оформить заказ-наряд на объекте за 1–2 минуты с телефона, даже если он работает одной рукой, в перчатках, в темном помещении, в шахте лифта и при нестабильном интернете.

## 1. Общая карта интерфейса

### 1.1 Роли и интерфейсные зоны

1. **Механик**
   - mobile-first PWA;
   - основной сценарий: объект → лифт → заказ-наряд → работы → материалы → фото → подпись → проверка → отправка;
   - интерфейс рассчитан на короткие действия, крупные кнопки и offline-first поведение.

2. **Диспетчер / офис**
   - desktop-first web workspace;
   - основной сценарий: очередь заказ-нарядов → проверка → подтверждение или возврат → PDF → контроль механиков;
   - интерфейс рассчитан на таблицы, split panels, фильтры, просмотр фото и массовый контроль.

3. **Руководитель**
   - desktop/tablet dashboard;
   - основной сценарий: KPI → проблемы → детализация по механикам, объектам, материалам, штрафам;
   - интерфейс рассчитан на аналитические панели, drill-down и управленческие отчеты.

### 1.2 Глобальная структура экранов

```text

MECHANIC
```

### 1.3 Главные UX-принципы

- Интерфейс механика всегда mobile-first.
- Основные touch-зоны не меньше 56 px по высоте.
- Текст короткий, функциональный, без рекламных формулировок.
- Самые частые действия доступны в один тап.
- Все формы имеют autosave.
- Offline mode показывается явно, но не блокирует оформление черновика.
- Критичные ошибки показываются прямо в проблемном блоке.
- Отправка заказ-наряда невозможна без обязательных фото, подписи и прохождения блокирующей валидации.
- Desktop-интерфейсы строятся вокруг рабочих очередей, таблиц и split workspace.

## 2. Глобальная навигация

## 2.1 Mobile navigation

### Назначение

Обеспечить механику доступ к основным рабочим зонам большим пальцем одной руки.

### Структура bottom navigation

Нижняя навигация содержит 4 постоянных пункта:

1. **Объекты** — список назначенных объектов и срочных заявок.
2. **Наряды** — история и черновики заказ-нарядов.
3. **Уведомления** — возвраты, срочные сообщения, sync-ошибки.
4. **Профиль** — смена, склад механика, статус синхронизации, выход.

### Floating actions

Используются только для контекстных рабочих действий:

- «+ Наряд» на карточке объекта;
- «Сделать фото» на экране фотофиксации;
- «Добавить работу» в блоке работ;
- «Добавить материал» в блоке материалов.

Floating action не должен перекрывать sticky submit area.

### Sticky buttons

На экране создания заказ-наряда нижняя панель всегда закреплена:

- слева: статус сохранения и сети;
- по центру: «Проверить»;
- справа: «Отправить» или «Исправить ошибки».

### Mobile состояния навигации

- **Online** — обычное отображение.
- **Offline** — верхний или нижний compact banner «Офлайн. Данные сохраняются».
- **Pending sync** — badge с количеством операций в очереди.
- **Critical return** — красно-оранжевый badge в «Наряды».
- **Session warning** — блокирующий переход на Session expired screen.

## 2.2 Desktop navigation

### Назначение

Обеспечить диспетчеру и руководителю быстрый переход между очередями, аналитикой и деталями без потери контекста.

### Sidebar

Левый sidebar:

- Dashboard;
- Заказ-наряды;
- Проверка;
- Фото-контроль;
- Механики;
- Объекты;
- Материалы;
- Штрафы;
- Отчеты;
- Настройки.

### Workspace layout

Desktop workspace строится как 3-зонная структура:

1. Sidebar — навигация.
2. Center panel — таблица, очередь или dashboard.
3. Right panel — детали выбранной записи, preview фото, комментарии или действия.

### Split panels

Для проверки заказ-наряда:

- слева: список заказ-нарядов;
- центр: содержимое заказ-наряда;
- справа: фото, AI-результаты, действия approve/reject.

### Desktop состояния навигации

- свернутый sidebar;
- закрепленная панель фильтров;
- сохранение выбранного фильтра;
- deep link на конкретный заказ-наряд;
- режим «только проблемные»;
- режим bulk review для диспетчера.

# 3. AUTH экраны

## 3.1 Login screen

### 1. Назначение

Позволить пользователю войти в систему с телефона, планшета или desktop. Экран должен быть максимально утилитарным и не содержать промо-контента.

### 2. Данные

- поле телефон/email/табельный номер;
- поле пароль или одноразовый код;
- текущий статус сети;
- версия приложения;
- статус PWA cache: «готово к offline» или «требуется сеть».

### 3. Действия

- ввести логин;
- ввести пароль;
- показать/скрыть пароль;
- войти;
- перейти к восстановлению пароля;
- повторить вход после ошибки сети.

### 4. Кнопки

- «Войти»;
- «Показать пароль»;
- «Забыли пароль?»;
- «Повторить» при сетевой ошибке.

### 5. Состояния

- initial;
- loading;
- wrong credentials;
- account blocked;
- no connection;
- cached session available;
- forced password reset;
- success redirect by role.

### 6. Mobile version

- один столбец;
- поля на всю ширину;
- кнопка входа высотой 56–64 px;
- крупный индикатор offline/online;
- клавиатура не должна закрывать кнопку входа.

### 7. Desktop version

- компактная форма в центре;
- служебная информация в нижней части;
- без иллюстраций и рекламных блоков.

### 8. Компоненты

- text input;
- password input;
- primary button;
- network status badge;
- inline alert;
- loading spinner;
- toast notification.

### 9. API

- `POST /auth/login`;
- `POST /auth/refresh` при наличии сохраненной сессии;
- `GET /auth/me` после успешного входа.

### 10. Ошибки

- неверный логин или пароль;
- пользователь заблокирован;
- нет сети;
- сервер недоступен;
- устройство не прошло политику безопасности;
- истек refresh-токен.

## 3.2 Password recovery

### 1. Назначение

Восстановить доступ без обращения к администратору, если политика компании это разрешает.

### 2. Данные

- телефон/email;
- одноразовый код;
- новый пароль;
- повтор нового пароля.

### 3. Действия

- запросить код;
- ввести код;
- установить новый пароль;
- вернуться ко входу.

### 4. Кнопки

- «Получить код»;
- «Проверить код»;
- «Сохранить пароль»;
- «Назад ко входу».

### 5. Состояния

- input identifier;
- code sent;
- code invalid;
- code expired;
- password policy error;
- success.

### 6. Mobile version

- пошаговый режим;
- один основной action на экране;
- крупный таймер повторной отправки кода.

### 7. Desktop version

- форма с пошаговым progress indicator;
- справа может быть служебный журнал попыток для admin-only режима, но не для обычного пользователя.

### 8. Компоненты

- stepper;
- OTP input;
- password input;
- alert;
- primary button.

### 9. API

- `POST /auth/password-recovery/request`;
- `POST /auth/password-recovery/verify`;
- `POST /auth/password-recovery/reset`.

### 10. Ошибки

- пользователь не найден;
- лимит попыток;
- код истек;
- пароль не соответствует политике;
- нет сети.

## 3.3 Session expired screen

### 1. Назначение

Безопасно обработать истекшую или отозванную сессию без потери локальных черновиков механика.

### 2. Данные

- причина: «сессия истекла», «вход выполнен на другом устройстве», «доступ отозван»;
- количество локальных несинхронизированных изменений;
- время последней синхронизации.

### 3. Действия

- повторно войти;
- сохранить локальные черновики;
- очистить устройство при требовании политики безопасности.

### 4. Кнопки

- «Войти снова»;
- «Сохранить черновики на устройстве»;
- «Очистить данные» для admin/security сценария.

### 5. Состояния

- session expired;
- token revoked;
- offline with expired token;
- local drafts exist;
- no local data.

### 6. Mobile version

- один критический alert;
- крупная кнопка повторного входа;
- отдельный блок «Черновики на устройстве».

### 7. Desktop version

- centered system screen;
- переход к login;
- при роли диспетчера local drafts обычно отсутствуют.

### 8. Компоненты

- blocking alert;
- status panel;
- primary button;
- secondary button.

### 9. API

- `POST /auth/refresh`;
- `GET /auth/me`;
- `POST /auth/logout` при очистке.

### 10. Ошибки

- refresh token invalid;
- сеть недоступна;
- local storage недоступен;
- security policy forbids offline access.

# 4. Механик

## 4.1 Главный экран механика — список объектов

### 1. Назначение

Показать механику все назначенные объекты, срочные заявки, непринятые/возвращенные заказ-наряды и состояние offline/sync.

### 2. Данные

- список объектов;
- адрес;
- заказчик;
- номер лифта или количество лифтов;
- тип работ;
- срочность;
- статус задания;
- наличие черновика;
- наличие возвращенного заказ-наряда;
- расстояние или район, если геоданные доступны;
- offline indicator;
- время последней синхронизации.

### 3. Действия

- открыть объект;
- продолжить черновик;
- открыть возвращенный наряд;
- отфильтровать срочные;
- найти объект по адресу или номеру лифта;
- обновить данные;
- открыть sync queue.

### 4. Кнопки

- «Обновить»;
- «Срочные»;
- «Черновики»;
- «Возвраты»;
- «Продолжить» на карточке черновика;
- «Открыть» на карточке объекта.

### 5. Состояния

- loading assignments;
- loaded;
- empty assignments;
- offline cached list;
- sync pending;
- urgent items present;
- returned work orders present;
- error loading assignments;
- stale data warning.

### 6. Mobile version

- карточки в одну колонку;
- крупный адрес;
- короткие badges: «Срочно», «ТО», «Ремонт», «Черновик», «Возврат»;
- sticky offline banner сверху или снизу;
- поиск раскрывается в полноэкранный input;
- фильтры горизонтальными chips.

### 7. Desktop version

- таблица или плотный list view;
- фильтры слева или сверху;
- right preview panel с выбранным объектом;
- keyboard shortcuts для диспетчерского режима недоступны механику по умолчанию.

### 8. Компоненты

- object card;
- status badge;
- priority badge;
- search input;
- filter chips;
- sync indicator;
- empty state;
- skeleton loader;
- toast.

### 9. API

- `GET /mobile/assignments`;
- `GET /mobile/sync`;
- `POST /mobile/sync` при наличии очереди;
- `GET /notifications?scope=mechanic`.

### 10. Ошибки

- нет сети и нет кэша;
- assignment был снят диспетчером;
- недостаточно прав;
- сервер недоступен;
- конфликт версии справочников.

## 4.2 Карточка объекта

### 1. Назначение

Дать механику быстрый контекст по объекту и выбранному лифту перед созданием заказ-наряда.

### 2. Данные

- адрес;
- заказчик;
- ответственное лицо и телефон;
- номер лифта;
- тип оборудования;
- производитель/модель;
- этажность/грузоподъемность при наличии;
- история ремонтов;
- последние замечания;
- последние использованные материалы;
- активные задания;
- предупреждения: доступ, опасность, повторная проблема.

### 3. Действия

- выбрать лифт;
- позвонить ответственному;
- посмотреть историю;
- открыть последние фото;
- создать заказ-наряд;
- продолжить существующий черновик;
- открыть карту, если геоданные доступны.

### 4. Кнопки

- «Создать заказ-наряд»;
- «Продолжить черновик»;
- «Позвонить»;
- «История»;
- «Последние фото»;
- «Назад».

### 5. Состояния

- object loading;
- object loaded;
- no elevator selected;
- multiple elevators;
- no history;
- offline cached object;
- object archived;
- assignment expired;
- access warning.

### 6. Mobile version

- шапка с адресом и badges;
- переключатель лифта крупными segmented buttons;
- история свернута accordion-блоками;
- кнопка создания закреплена снизу;
- телефон ответственного вызывается через native call action.

### 7. Desktop version

- two-column layout;
- слева карточка объекта и лифтов;
- справа история, замечания, последние наряды;
- кнопка создания в верхней панели действий.

### 8. Компоненты

- details card;
- elevator selector;
- timeline;
- accordion;
- call action button;
- warning alert;
- sticky action bar.

### 9. API

- `GET /mobile/buildings/:id`;
- `GET /mobile/elevators/:id/history`;
- `GET /mobile/work-orders?buildingId=&elevatorId=`;
- `POST /mobile/work-orders` при создании черновика.

### 10. Ошибки

- объект не найден;
- лифт не активен;
- механик больше не назначен;
- история недоступна offline;
- ошибка создания черновика.

- не выбран лифт;
- не добавлены работы;

- обязательное фото отсутствует;

- AI отметил фото как нечитаемое;

- конфликт статуса;
- заказ-наряд уже подтвержден офисом.

### 4.3.1 Шапка заказ-наряда

#### Назначение

Сразу показать, что механик оформляет наряд по правильному объекту, лифту и заказчику.

#### Данные

- номер заказ-наряда или temporary draft id;
- заказчик;
- адрес;
- номер лифта;
- дата;
- механик;
- тип работ;
- срочность;
- статус.

#### UX-логика

- большинство полей readonly;
- изменение лифта возможно только до добавления работ/материалов или через подтверждение;
- при offline режиме номер может быть временным;
- шапка сворачивается после первого экрана, но статус и адрес остаются видимыми.

### 4.3.2 Блок «Работы»

#### Назначение

Зафиксировать выполненные работы быстро и без ручного длинного ввода.

#### Данные

- действие;
- элемент;
- количество;
- единица;
- комментарий;
- источник: шаблон, поиск, ручной ввод.

#### UX-логика

# 8. Состояния интерфейса

## 8.1 Loading states

- skeleton для списков и карточек;
- progress bar для upload/compression;
- blocking loader только при невозможности продолжить;
- optimistic UI для добавления работ и материалов.

## 8.2 Offline states

- постоянный offline indicator;
- пояснение «Данные сохраняются на устройстве»;
- кнопка «Открыть очередь»;
- запрет только тех действий, которые требуют сервера немедленно;
- создание и редактирование черновика остается доступным.

## 8.3 Empty states

- список объектов пуст: «Нет назначенных объектов»;
- история пуста: «Заказ-нарядов пока нет»;
- очередь диспетчера пуста: «Нет нарядов на проверке»;
- материалы не добавлены: показать кнопку «Без материалов» и «+ Материал»;
- фото не добавлено: показать обязательные слоты.

Empty state не должен быть рекламным или декоративным.

## 8.4 Error states

- inline error рядом с полем;
- section error в блоке заказ-наряда;
- page error для недоступного API;
- storage error для фото;
- conflict error для sync;
- security error для прав доступа.

## 8.5 Validation states

- neutral: еще не проверялось;
- checking: проверяется;
- passed: успешно;
- warning: можно отправить, но есть риск;
- blocked: отправка запрещена;
- stale: требуется повторная проверка.

## 8.6 Success states

- saved locally;
- synced;
- submitted;
- approved;
- PDF ready;
- material write-off completed.

# 9. Offline UX

## 9.1 Локальное сохранение

### Что сохраняется локально

- assignments;
- карточки объектов;
- справочник работ;
- справочник материалов;
- черновики заказ-нарядов;
- работы;
- материалы;
- фото в локальном blob storage;
- подписи;
- операции sync queue.

### UX-отображение

- «Сохранено на устройстве»;
- «Ожидает отправки»;
- «Фото ожидает загрузки»;
- «Справочник обновлен 08.05.2026 09:10»;
- «Остатки склада могут быть устаревшими».

## 9.2 Queue synchronization

### Логика

Каждое действие механика превращается в операцию очереди:

- создать черновик;
- обновить шапку;
- добавить работу;
- добавить материал;
- добавить фото;
- сохранить подпись;
- отправить заказ-наряд.

### UX

- очередь доступна из профиля и offline banner;
- операции сгруппированы по заказ-наряду;
- пользователь видит, что уже отправлено, а что ожидает;
- failed операции имеют кнопку «Повторить»;
- duplicate submit не допускается.

## 9.3 Reconnect flow

1. Система обнаруживает сеть.
2. Показывает toast «Сеть восстановлена. Синхронизируем…».
3. Начинает upload фото и подписи.
4. Отправляет metadata.
5. Отправляет операции заказ-наряда.
6. Запускает server validation.
7. Обновляет статусы.
8. Показывает результат.

### Состояния reconnect

- reconnect detected;
- uploading files;
- syncing data;
- validating;
- success;
- partial success;
- conflict;
- failed.

## 9.4 Pending uploads

### UX

- каждый фото-слот показывает pending badge;
- общий счетчик pending uploads в sticky bar;
- отправка в офис может быть поставлена в очередь, но статус остается «ожидает sync»;
- если файл поврежден локально, пользователь видит необходимость переснять фото.

## 9.5 Conflict resolution

### Возможные конфликты

- объект снят с назначения;
- заказ-наряд уже изменен офисом;
- складской остаток изменился;
- фото metadata отправлено, но файл не загрузился;
- черновик был отправлен с другого устройства.

### UX

- отдельный экран «Нужна проверка»;
- понятное объяснение;
- варианты:
  - «Сохранить мои данные и отправить диспетчеру»;
  - «Обновить данные и повторить»;
  - «Создать копию черновика»;
  - «Отменить локальные изменения» только после подтверждения.

# 10. AI UX

## 10.1 Общая логика AI-проверки

AI должен быть помощником, а не непонятным блокером. Каждый AI-результат обязан объяснять, что не так и как исправить.

### Статусы

- «Проверяется»;
- «OK»;
- «Предупреждение»;
- «Нужно исправить»;
- «AI временно недоступен».

## 10.2 Плохое фото

### Сценарии

- размыто;
- слишком темно;
- засвет;
- низкое разрешение;
- часть детали не в кадре.

### UX

- на фото появляется badge «Плохое качество»;
- ниже — короткая причина;
- основная кнопка: «Переснять»;
- secondary: «Оставить с предупреждением» только если ошибка не blocking.

## 10.3 Отсутствие подписи

### UX

- блок «Подпись» подсвечивается как blocking;
- sticky button показывает «Нужна подпись»;
- кнопка «Перейти к подписи» скроллит или открывает экран подписи;
- отправка недоступна.

## 10.4 Нечитабельный заказ-наряд

### UX

- фото заказ-наряда получает статус «Нечитабельно»;
- показывается рекомендация: «Сфотографируйте ближе, без бликов»;
- диспетчер видит OCR confidence;
- механик должен переснять, если ошибка blocking.

## 10.5 Несоответствие фото типу работы

### Примеры

- работа: «Замена роликов», а фото не содержит детали;
- обязательный слот «демонтированная деталь» похож на установленную;
- фото заказ-наряда загружено в слот детали.

### UX

- warning или blocking в зависимости от confidence;
- кнопка «Переместить фото в другой слот»;
- кнопка «Переснять»;
- поле комментария «Объяснить диспетчеру» для warning-сценария.

## 10.6 AI недоступен

### UX

- если базовые обязательные поля заполнены, заказ-наряд можно поставить в очередь проверки;
- статус: «AI недоступен, проверит офис»;
- диспетчер видит такой наряд в отдельном фильтре;
- если политика требует AI до отправки, sticky button показывает «Ожидаем проверку».

# 11. Design system

## 11.1 Цвета

### Основная палитра

- `Dark Navy` — базовый фон приложения;
- `Graphite` — поверхности карточек и панелей;
- `Steel Gray` — границы, разделители, вторичный текст;
- `Industrial Orange` — главный action, срочность, акценты;
- `Signal Red` — blocking errors и критические возвраты;
- `Amber` — offline, pending sync, warnings;
- `Muted Green` — success, synced, approved;
- `Cold Blue` — informational и системные статусы.

### UX-правила цвета

- цвет всегда дублируется текстом или иконкой;
- orange используется для действий и срочности, не для декора;
- red используется только для блокирующих проблем;
- dark mode является основным режимом, а не дополнительным.

## 11.2 Typography

### Mobile

- заголовок экрана: 20–22 px;
- адрес объекта: 18–20 px, semibold;
- основной текст: 16 px;
- вторичный текст: 13–14 px;
- кнопки: 16–18 px, semibold;
- badges: 12–13 px, uppercase optional только для коротких статусов.

### Desktop

- заголовки разделов: 22–28 px;
- таблицы: 13–14 px;
- карточки KPI: 24–32 px для значения;
- labels: 12–13 px.

## 11.3 Spacing

### Mobile

- внешний padding: 12–16 px;
- расстояние между секциями: 12–16 px;
- кнопки: высота 56–64 px;
- input: высота 52–56 px;
- bottom nav: 64–72 px;
- sticky submit area: 72–88 px с учетом safe area.

### Desktop

- sidebar width: 240–280 px;
- collapsed sidebar: 72 px;
- panel gap: 16–24 px;
- table row height: 44–52 px;
- right drawer: 360–520 px.

## 11.4 Button sizes

### Mobile

- primary action: 56–64 px height;
- secondary action: 48–56 px;
- icon button: минимум 48 x 48 px;
- dangerous action не размещать рядом с primary без разделения.

### Desktop

- primary: 40–44 px;
- table row action: 32–36 px;
- toolbar button: 36–40 px.

## 11.5 Touch targets

- минимум 48 x 48 px;
- рекомендуемый размер для механика: 56 x 56 px;
- расстояние между критичными actions: минимум 8–12 px;
- swipe actions не должны быть единственным способом выполнить действие.

## 11.6 Dark mode

Dark mode — основной industrial режим:

- снижает ослепление в темных технических помещениях;
- повышает читаемость контрастных статусов;
- поддерживает OLED battery efficiency;
- должен иметь high-contrast вариант для солнца/фонаря.

## 11.7 Industrial visual style

Визуальный стиль:

- плотные рабочие панели;
- четкие границы;
- минимум декоративных иллюстраций;
- функциональные иконки;
- status-first интерфейс;
- никаких hero blocks, feature cards, маркетинговых CTA или promo UI;
- ощущение warehouse/maintenance software, а не startup landing.

# 12. End-to-end user flows

## 12.1 Быстрое оформление заказ-наряда механиком

1. Механик открывает PWA.
2. Видит главный экран «Объекты».
3. Выбирает срочный объект.
4. Открывает карточку объекта.
5. Проверяет адрес и лифт.
6. Нажимает «Создать заказ-наряд».
7. Добавляет работу из шаблона.
8. Добавляет материал из подсказки или выбирает «Без материалов».
9. Делает 3 обязательных фото.
10. Получает подпись заказчика.
11. Нажимает «Проверить».
12. Исправляет ошибки, если есть.
13. Нажимает «Отправить».
14. При сети заказ-наряд уходит на проверку.
15. Без сети заказ-наряд получает статус «В очереди».

## 12.2 Возврат заказ-наряда диспетчером

1. Диспетчер открывает dashboard.
2. Переходит в «На проверке».
3. Открывает заказ-наряд.
4. Видит AI warning по фото.
5. Открывает фото viewer.
6. Подтверждает, что фото нечитаемое.
7. Нажимает «Вернуть».
8. Указывает структурированную причину.
9. Механик получает уведомление.
10. Заказ-наряд появляется у механика в «Возвраты».
11. Механик переснимает фото.
12. Повторно отправляет.

## 12.3 Управленческий контроль проблемных объектов

1. Руководитель открывает dashboard.
2. Видит рост повторных ремонтов.
3. Открывает heatmap проблемных объектов.
4. Выбирает объект с высоким risk score.
5. Смотрит историю лифтов.
6. Открывает расход материалов.
7. Сравнивает с другими объектами.
8. Экспортирует отчет.
9. Передает задачу диспетчеру или ответственному руководителю.

# 13. Product guardrails

1. Не создавать маркетинговые экраны или промо-компоненты.
2. Не добавлять hero sections, pricing, testimonials, feature cards.
3. Любой экран должен иметь операционную задачу.
4. Mobile UX механика важнее визуальной декоративности.
5. Offline-first не является дополнительной функцией — это базовый режим работы.
6. Ошибки должны объяснять, что делать дальше.
7. Диспетчерский интерфейс должен ускорять проверку, а не копировать бумажный процесс.
8. Руководительский dashboard должен вести к действиям: открыть проблему, сравнить, экспортировать, назначить ответственность.
