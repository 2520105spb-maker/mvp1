# НеоЛифт — архитектура внутренней ERP/PWA системы заказ-нарядов

## 0. Назначение системы

«НеоЛифт ERP» — внутренняя mobile-first PWA система для механиков, диспетчеров, офисных сотрудников и руководителей лифтовой компании. Система заменяет бумажные заказ-наряды, ручные фотоотчеты в мессенджерах и последующее дублирование данных в офисе.

Главная продуктовая цель: механик должен оформить корректный заказ-наряд на объекте за 1–2 минуты с телефона, включая работы, материалы, обязательные фотографии и подпись заказчика.

Система не содержит маркетинговых, промо- или лендинговых разделов. Все экраны являются рабочими интерфейсами ERP/field-service класса.

## 1. Полная архитектура системы

### 1.1 Архитектурный стиль

Система проектируется как модульная web ERP/PWA платформа:

- mobile-first frontend на Next.js, React, TypeScript, Tailwind и shadcn/ui;
- backend API на NestJS;
- PostgreSQL как основная транзакционная база данных;
- S3-compatible storage для фотографий, подписей и PDF;
- JWT-аутентификация и RBAC-модель доступа;
- offline-first PWA слой для механиков;
- серверный модуль AI-проверки заказ-нарядов;
- событийная модель для списания материалов, уведомлений и контроля штрафов.

### 1.2 Логические контуры

1. **Mobile mechanic PWA**
   - авторизация;
   - список назначенных объектов;
   - карточка объекта и лифта;
   - создание заказ-наряда;
   - фотофиксация;
   - подпись заказчика;
   - локальное автосохранение;
   - синхронизация при появлении сети.

2. **Office dispatcher web app**
   - очередь заказ-нарядов на проверку;
   - просмотр всех данных, фотографий и AI-результатов;
   - возврат на доработку;
   - подтверждение;
   - экспорт PDF;
   - контроль механиков и фотофиксации.

3. **Management dashboard**
   - сводка по статусам;
   - статистика механиков;
   - статистика объектов и лифтов;
   - расход материалов;
   - штрафы и нарушения регламентов;
   - SLA и просрочки.

4. **Backend services**
   - Auth/RBAC;
   - Users/Mechanics;
   - Customers/Buildings/Elevators;
   - WorkOrders;
   - Materials/Warehouse;
   - Photos/Signatures;
   - AI Validation;
   - Notifications;
   - PDF Export;
   - Audit Log.

5. **Infrastructure**
   - PostgreSQL;
   - Redis или совместимое хранилище очередей для фоновых задач;
   - S3-compatible object storage;
   - CDN/private signed URLs для файлов;
   - observability: logs, metrics, traces;
   - backup и retention policies.

### 1.3 Принцип проектирования заказ-наряда

Заказ-наряд — центральная сущность системы. Он проходит жизненный цикл:

`Черновик → Заполнен → На проверке → Возвращен → На проверке → Подтвержден → Закрыт`

Отправка заказ-наряда механиком возможна только если:

- заполнен объект и лифт;
- указана минимум одна выполненная работа;
- материалы указаны корректно или явно отмечено, что материалы не использовались;
- загружены все обязательные фото;
- сохранена подпись заказчика;
- AI-проверка не нашла блокирующих ошибок;
- локальные изменения синхронизированы или поставлены в гарантированную очередь отправки.

## 2. Структура экранов

### 2.1 Экран авторизации

Назначение: быстрый вход механика, диспетчера или руководителя.

Содержимое:

- логотип/название системы в компактной форме;
- поле телефона, email или табельного номера;
- поле пароля или одноразового кода;
- кнопка входа с большой touch-зоной;
- индикатор сети;
- сообщение о последней синхронизации;
- служебная ссылка «Проблема со входом».

Особенности:

- без промо-блоков;
- без маркетинговых описаний;
- при потере сети разрешается вход по последней валидной сессии, если refresh-токен и локальная политика безопасности это позволяют.

### 2.2 Экран списка объектов механика

Назначение: показать механику только назначенные на него объекты и срочные задачи.

Карточка объекта содержит:

- адрес;
- номер лифта или несколько лифтов;
- статус задачи;
- тип работ: ТО, ремонт, аварийная заявка, повторный выезд;
- срочность;
- индикатор незавершенного черновика;
- offline-статус данных.

Фильтры:

- сегодня;
- срочные;
- черновики;
- возвращенные;
- рядом/по маршруту;
- по адресу или номеру лифта.

### 2.3 Экран карточки объекта

Содержит:

- адрес;
- заказчик;
- контакт ответственного лица;
- список лифтов;
- выбранный номер лифта;
- тип лифта и базовые технические данные;
- история работ;
- последние ремонты;
- последние замечания диспетчера;
- складские подсказки по часто используемым материалам;
- большая кнопка «Создать заказ-наряд»;
- кнопка продолжения черновика, если он уже создан.

### 2.4 Экран создания заказ-наряда

Это главный экран системы для механика.

#### Шапка

Автоматически подставляется:

- заказчик;
- адрес;
- номер лифта;
- дата и время;
- механик;
- тип работ;
- номер задания или заявки, если есть.

Редактируемые поля ограничены правами и контекстом. Механик не должен тратить время на повторный ввод известных данных.

#### Блок «Работы»

Поля одной строки работы:

- действие;
- элемент;
- количество;
- комментарий при необходимости.

Механизмы ускорения:

- быстрые шаблоны;
- autocomplete;
- поиск по словарю работ;
- избранные работы механика;
- работы по типу лифта;
- последние работы на этом объекте;
- добавление одной кнопкой.

Примеры шаблонов:

- «Замена кнопок вызова»;
- «Регулировка дверей»;
- «Замена роликов»;
- «Замена контакта ДК»;
- «Чистка поста приказов»;
- «Проверка цепи безопасности».

#### Блок «Материалы»

Поля одной строки материала:

- название;
- тип;
- количество;
- единица измерения;
- доступный остаток на складе;
- источник списания: склад механика, центральный склад, аварийный резерв.

Правила:

- после подтверждения заказ-наряда материалы автоматически списываются;
- если остатка недостаточно, система предупреждает механика и отправляет событие диспетчеру;
- для черновика создается резерв или предварительное списание в зависимости от политики склада;
- при возврате заказ-наряда списание не финализируется, если заказ-наряд еще не подтвержден.

#### Блок «Фотофиксация»

Обязательные фото:

1. установленная деталь;
2. демонтированная деталь;
3. заказ-наряд.

Интерфейс:

- крупные зоны загрузки;
- mobile camera upload;
- drag and drop для desktop/tablet режима;
- preview;
- пересъемка одной кнопкой;
- локальная компрессия;
- индикатор загрузки в S3;
- статус AI-проверки каждого фото.

#### Блок «AI-проверка»

Показывает компактный чек-лист:

- фото установлено;
- фото демонтированной детали добавлено;
- фото заказ-наряда добавлено;
- фото читаемое;
- подпись найдена;
- работы заполнены;
- материалы заполнены или отмечено «не использовались»;
- нет блокирующих ошибок.

Если есть блокирующая ошибка, кнопка отправки заблокирована.

#### Блок подписи

Содержит:

- canvas-поле для подписи пальцем или стилусом;
- кнопку очистки;
- кнопку сохранения;
- превью сохраненной подписи;
- имя подписанта;
- должность/роль подписанта;
- время подписи;
- геометку при разрешении пользователя и политике компании.

#### Sticky actions

Внизу экрана всегда доступны:

- «Сохранить черновик»;
- «Проверить»;
- «Отправить»;
- индикатор offline/sync.

### 2.5 Экран заказ-нарядов механика

Содержит:

## 3. User flow

### 3.1 Основной flow механика

1. Механик входит в систему.
2. Видит список назначенных объектов.
3. Открывает объект.
4. Выбирает лифт.
5. Нажимает «Создать заказ-наряд».
6. Проверяет автозаполненную шапку.
7. Добавляет работы через шаблоны или поиск.
8. Добавляет материалы или выбирает «материалы не использовались».
9. Делает обязательные фото.
10. Получает подпись заказчика.
11. Запускает проверку.
12. Исправляет ошибки, если они есть.
13. Отправляет заказ-наряд.
14. Система синхронизирует данные с офисом.
15. Диспетчер получает заказ-наряд в очередь проверки.

### 3.2 Flow возврата на доработку

1. Диспетчер открывает заказ-наряд.
2. Видит ошибку: например, нечитаемое фото или неверный материал.
3. Указывает причину возврата.
4. Статус меняется на «Возвращен».
5. Механик получает уведомление.
6. Механик открывает заказ-наряд.
7. Система подсвечивает только проблемные блоки.
8. Механик исправляет данные.
9. Повторно отправляет на проверку.

### 3.3 Flow закрытия заказ-наряда

1. Диспетчер подтверждает корректность.
2. Материалы финально списываются со склада.
3. Генерируется PDF.
4. Заказ-наряд получает статус «Подтвержден».
5. После бухгалтерской или управленческой обработки статус становится «Закрыт».

### 6.3 API принципы

- Все критичные операции пишутся в audit log.
- Файлы загружаются напрямую в S3 по signed URL, API хранит только metadata.
- Диспетчерские и управленческие запросы используют пагинацию, фильтры и сортировку.

## 8. Offline logic

### 8.1 Что должно работать без сети

- открытие назначенных объектов, заранее загруженных на устройство;
- просмотр карточки объекта;
- создание черновика;
- добавление работ;
- добавление материалов из локального справочника;
- фотофиксация с локальным хранением;
- подпись;
- локальная проверка обязательных полей;
- постановка заказ-наряда в очередь отправки.

### 8.2 Локальное хранилище

Для PWA:

- IndexedDB для структурированных данных;
- Cache Storage для shell приложения и справочников;
- Blob/File storage в IndexedDB для временного хранения фото и подписей;
- service worker для кэширования и фоновой синхронизации;
- local encryption для чувствительных данных при необходимости политики безопасности.

### 8.3 Sync queue

Каждое действие механика записывается как операция:

- `CREATE_WORK_ORDER`;
- `UPSERT_WORK_ITEM`;
- `UPSERT_MATERIAL`;
- `ADD_PHOTO`;
- `SAVE_SIGNATURE`;
- `SUBMIT_WORK_ORDER`.

У каждой операции есть:

- `client_operation_id`;
- `offline_client_id`;
- timestamp;
- payload;
- status;
- retry_count;
- dependency list.

### 8.4 Конфликты

Вероятные конфликты:

- объект переназначен другому механику;
- лифт снят с обслуживания;
- материал закончился на складе;
- заказ-наряд уже возвращен или подтвержден офисом.

Политика:

- действия механика не теряются;
- backend возвращает conflict response;
- UI показывает понятный экран разрешения;
- критичные конфликты отправляются диспетчеру.

## 9. File storage logic

### 9.1 Типы файлов

- фото установленной детали;
- фото демонтированной детали;
- фото заказ-наряда;
- подпись;
- PDF заказ-наряда;
- preview thumbnails.

### 9.2 Поток загрузки фото

1. Механик делает фото.
2. Клиент сжимает фото до регламентного размера.
3. Клиент считает checksum.
4. Backend выдает signed upload URL.
5. Клиент загружает файл в S3.
6. Клиент отправляет metadata в API.
7. Backend создает запись `Photos`.
8. Validation service ставит фото в очередь AI-проверки.
9. UI получает статус проверки.

### 9.3 Структура ключей S3

Рекомендуемый формат:

`work-orders/{yyyy}/{mm}/{work_order_id}/photos/{photo_type}/{photo_id}.jpg`

Для подписей:

`work-orders/{yyyy}/{mm}/{work_order_id}/signatures/{signature_id}.png`

Для PDF:

`work-orders/{yyyy}/{mm}/{work_order_id}/pdf/{work_order_number}.pdf`

### 9.4 Безопасность файлов

- bucket не публичный;
- доступ только через signed URLs;
- срок жизни signed URL ограничен;
- все обращения к файлам логируются;
- PDF может иметь watermark и номер версии;
- удаление файлов — soft-delete через metadata и lifecycle policy.

## 10. AI-validation logic

### 10.1 Цель AI-проверки

AI-проверка не заменяет диспетчера, а блокирует очевидно некорректные заказ-наряды до отправки и ускоряет офисную проверку.

### 10.2 Проверки до отправки

Система проверяет:

- наличие всех обязательных фото;
- минимальное разрешение фото;
- размытость;
- засветы и темноту;
- наличие объекта в кадре;
- читаемость фото заказ-наряда;
- наличие подписи на фото заказ-наряда, если применимо;
- наличие электронной подписи в canvas;
- полноту заполнения работ;
- корректность материалов;
- несоответствия между работами и материалами.

### 10.3 Уровни ошибок

1. **Blocking** — нельзя отправить:
   - нет обязательного фото;
   - нет подписи;
   - фото полностью нечитаемое;
   - не указаны работы;
   - отрицательное или нулевое количество материала.

2. **Warning** — можно отправить, но будет видно диспетчеру:
   - качество фото среднее;
   - материал нехарактерен для выбранной работы;
   - нет геометки;
   - работа не из справочника.

3. **Info** — подсказка:
   - найден похожий шаблон;
   - часто используемый материал не добавлен.

### 10.4 AI pipeline

1. File metadata validation.
2. Image quality validation.
3. OCR для фото заказ-наряда.
4. Signature detection.
5. Business rules validation.
6. Risk score calculation.
7. Result persistence.
8. UI notification.

### 10.5 Результат проверки

Для каждого заказ-наряда хранится:

- общий статус проверки;
- список ошибок;
- список предупреждений;
- score качества;
- version validation model;
- дата проверки;
- кто или что инициировало проверку.

## 11. Roles & permissions

### 11.1 Роли

1. `MECHANIC` — механик.
2. `DISPATCHER` — диспетчер/офис.
3. `MANAGER` — руководитель.
4. `ADMIN` — системный администратор.

### 11.2 Права механика

Разрешено:

- входить в систему;
- видеть назначенные объекты;
- создавать заказ-наряды по своим объектам;
- редактировать свои черновики и возвращенные заказ-наряды;
- добавлять работы;
- добавлять материалы;
- загружать фото;
- сохранять подпись;
- отправлять на проверку;
- видеть свои заказ-наряды.

Запрещено:

- видеть все заказ-наряды компании;
- подтверждать заказ-наряды;
- менять складские остатки напрямую;
- удалять подтвержденные фото;
- менять чужие заказ-наряды.

### 11.3 Права диспетчера

Разрешено:

- видеть все заказ-наряды;
- фильтровать по статусам, механикам и объектам;
- проверять фото;
- возвращать на доработку;
- подтверждать заказ-наряды;
- экспортировать PDF;
- видеть контроль фотофиксации;
- видеть базовую статистику механиков.

Ограничено:

- изменение справочников;
- списание материалов вручную только по отдельному праву;
- управление ролями недоступно.

### 11.4 Права руководителя

Разрешено:

- видеть dashboard;
- видеть аналитику по механикам;
- видеть аналитику по объектам;
- контролировать штрафы;
- контролировать расход материалов;
- выгружать отчеты;
- видеть показатели качества и просрочки.

### 11.5 Права администратора

Разрешено:

- управление пользователями;
- управление ролями;
- настройка справочников;
- настройка складов;
- настройка обязательных фото;
- настройка AI-порогов;
- аудит доступа.

## 15. Ключевые продуктовые ограничения

1. Механик не должен вводить вручную данные, которые система уже знает.
2. Отправка невозможна без обязательных фото и подписи.
3. Offline-черновик не должен теряться при закрытии браузера или потере сети.
4. Диспетчер должен видеть причину ошибки без открытия каждого файла вручную.
5. Складские списания должны быть связаны с подтвержденными заказ-нарядами.
6. Все изменения статусов должны быть аудируемыми.
7. UI должен оставаться рабочим на маленьком экране и в тяжелых полевых условиях.
8. Система не должна превращаться в маркетинговый сайт: только рабочие ERP-интерфейсы.
